### S1.1 auth 模块

| # | 验收项 | 判定标准 |
|---|---|---|
| S1.1-1 | `POST /api/v1/auth/login` 账号密码登录 | seed 账号（`admin` / `sub01` / `sub02` / `clerk01`，密码 `Test@123456`）能登录并返回 `accessToken` + 角色 + 权限码 + 商家上下文 |
| S1.1-2 | 登录失败用例 | 密码错误 → 401；账号不存在 → 401；账号 `status=DISABLED` → 403。**不返回 500，不泄露「账号是否存在」** |
| S1.1-3 | `GET /api/v1/auth/profile` | 返回当前账号信息（含商家名、门店名、角色列表） |
| S1.1-4 | `PUT /api/v1/auth/password` | 旧密码校验通过才允许改；改后旧密码立即失效 |
| S1.1-5 | `GET /api/v1/auth/permissions` | 返回该账号的角色码与权限码数组 |
| S1.1-6 | JwtAuthGuard | 缺失/过期/篡改 token → 401；合法 token → 放行并把 payload 注入 `req.user` |
| S1.1-7 | RolesGuard | 无对应角色的账号访问受保护接口 → 403 |
| S1.1-8 | **MerchantScopeGuard 越权拦截（重点）** | 附属商家 A 的 token 请求 `merchantId=B` 或访问属 B 的资源 → **403**（不是返回 B 的数据）。详见下方「越权专项用例」 |

#### 越权专项用例（S1.1 必过，不可跳过）

```bash
# 1) 用附属商家 A 登录拿 token
curl -X POST http://localhost/api/v1/auth/login -H "Content-Type: application/json" \
  -d '{"username":"sub01","password":"Test@123456"}'

# 2) 携带 A 的 token，显式传 merchantId=B（B 是另一个商家）
curl -H "Authorization: Bearer <A的token>" \
  "http://localhost/api/v1/sub/stores?merchantId=<B的merchantId>"

# 期望：403 + reasonCode=FORBIDDEN_SCOPE / STORE_NOT_OWNED
# 禁止：返回 200 且 data 里是 B 的门店

# 3) 直接访问属于 B 的资源主键
curl -H "Authorization: Bearer <A的token>" \
  "http://localhost/api/v1/sub/stores/<B某门店id>"

# 期望：403 或 404（不得返回该门店详情）

# 4) 反向：B 的 token 访问自己的资源应正常
curl -H "Authorization: Bearer <B的token>" \
  "http://localhost/api/v1/sub/stores?merchantId=<B的merchantId>"
# 期望：200 + B 自己的数据
```

> 判定要点：Guard 必须从 **JWT** 取 `merchantId` / `storeId`，**忽略并覆盖**前端传入的值。
> 若发现「传了别人的 merchantId 就查到别人数据」，直接判定 S1.1 不通过。

| # | 验收项 | 判定标准 |

| S1.2-1 | `POST /api/v1/merchants/applications` 提交入驻申请 | 公开接口（`@Public`），落库 `status=PENDING`，自动挂到唯一的主体商家下 |

### S1.2 加固（进 S1.3 前，2026-10-06）

| # | 验收项 | 判定标准 |
|---|---|---|
| F-1 | `NODE_ENV` 默认安全 | `docker-compose.yml` 为 `${NODE_ENV:-production}`；`.env` 显式 `NODE_ENV=development`。没配的时候必须是**生产**，Swagger 默认关闭 |
| F-2 | 停用即时生效 | `JwtAuthGuard` 每次请求回表查 `admin_users.status` 与 `merchants.status`，非 `ACTIVE` / `APPROVED` 直接 401 —— **已签发的旧 token 立刻失效** |
| F-3 | 上传魔数校验 | 只认文件头：`png=89 50 4E 47`、`jpeg=FF D8 FF`、`pdf=25 50 44 46`、`webp=RIFF....WEBP`；与声明的 Content-Type 不符一律 400 `INVALID_FILE_TYPE` |
| F-4 | 首次登录强制改密 | 审核生成的账号 `must_change_password=true`；登录返回 `mustChangePassword:true`；未改密前除 `PUT /auth/password` 外一律 403 `PASSWORD_CHANGE_REQUIRED`；改密成功后自动置 false |
| F-5 | 入驻申请限流 | 同 IP 每小时 3 次，第 4 次起 429 `RATE_LIMITED` |
| F-6 | 审核并发安全 | 走事务 + 条件更新 `UPDATE ... WHERE id=? AND status='PENDING'`，影响行数 0 → 409；同时发两个 approve 只能有一个 201 |
| F-7 | parentId 不硬编码 / XFF | `parentId` 由 `SELECT id FROM merchants WHERE type='MAIN' LIMIT 1` 得出；Nginx 三个 location 均已透传 `X-Forwarded-For`，后端 `trust proxy` 只信前一跳 |

```
字符集：23456789ABCDEFGHJKMNPQRSTUVWXYZ（31 个 = 36 − 0/1/O/I/L）
结构：11 位 crypto 随机位（拒绝采样消除取模偏差） + 1 位校验位（位置加权 mod 31）
样例：RM9PRCWZP2A9 / Y8AMRDXPG6TM / TM39GB2EJ6VC（均为 seed 实际产出，末位为校验位）

**校验位字符集澄清（S2.3 验收前提出的疑问）**

| 项 | 结论 |
|---|---|
| 前 11 位字符集 | `23456789ABCDEFGHJKMNPQRSTUVWXYZ`（31 个） |
| 第 12 位校验位字符集 | **同一个**（31 个），不是全 36 字符 |
| 映射规则 | `check = CHARSET[(Σ (idx(cᵢ)+1) × (i+1)) mod 31]`，位置加权，可拦错一位与相邻写反 |
| 是否可能混入 0/O/1/I/L | **不可能**。校验位是 `CHARSET[sum % 31]`，取值域就是那 31 个字符 |

> 之前文档里的样例 `EYA9EV35MWF0` 是抄写错误（库内实际为 `EYA9EV35MWFM`，末位 `M`）。
> 已做 30 万次采样验证：校验位出现过的字符恰好是 31 个字符集的**全集**，不含 `0/O/1/I/L`。
```

> docs/02 写「共 32 个字符」与「去掉 0/O/1/I/L」矛盾（36−5=31）；按显式排除规则取 **31**，
> 31^11 ≈ 2.5×10^16，不影响唯一性，未为凑 32 放回 L。

**冲正使用场景**（reverse 的真实口径，此前待办要求补充）：
1. **订单取消 / 退款** —— 结账前用户反悔，券必须退回，否则用户资产凭空消失；
2. **误核销** —— 店员扫错码 / 核错单，当场冲正后重新核销正确的券；
3. **异常订单处理（S3）** —— 订单被标记 ABNORMAL 且判定券不应参与结算时冲正。
冲正**不是删除**：记录保留为 `REVERSED` 供对账追溯；券回 `UNUSED`（usedAt 清空）、券码回 `ISSUED`、模板 `usedCount−1`、订单解绑（`couponInstanceId=NULL`、discount=0、payAmount=totalAmount）。已实测冲正后四张表数据一致。

**订单与核销的关系**：核销必须挂订单（`orderNo` 必填）。订单已存在则条件绑定（`WHERE couponInstanceId IS NULL`，并发不绑重）并校验归属用户；不存在则按 `orderNo` 创建 CONSUME 订单（收银台「先核销后结账」场景），金额取 `orderAmount ?? faceValue`，抵扣 = `min(faceValue, orderAmount)`。

### S3.1 积分账户 + 积分流水 + 消费录单（2026-10-07 交付待验收）

> S3 分四批（S3.1 账户/流水/送分 → S3.2 兑换 → S3.3 过期清零 → S3.4 订单与异常处理），每批停下来单独验收。
> 积分模块比券模块更凶险的三个原因：**批次多过期点**（FIFO）、**金额类并发**（错账难追溯）、
> 异常订单**跨三张表的长事务**——S3.1 先把账户模型的底座打对。

#### 数据模型（schema 落地，无新增表）

- `point_accounts`：`balance / totalEarned / totalSpent / totalExpired / version`（乐观锁）。
- `point_transactions`：`type`（EARN/SPEND/EXPIRE/REFUND/ADJUST）、`amount` 带符号、
  **`remainingAmount`**（批次剩余，FIFO 扣减对象）、`balanceAfter`（对账口径）、`expireAt`（批次有效期）。
- 新增数据库约束（`server/prisma/sql/s31-point-constraints.sql`，幂等脚本已执行验证）：
  - `uniq_point_earn_order`（UNIQUE `(relatedOrderId, type)`）——同一订单只送一次积分；
    `relatedOrderId=NULL` 的流水不受影响（MySQL 唯一索引 NULL 互不相等，人工调整不冲突）；
  - `idx_point_fifo`（`(userId, expireAt, remainingAmount)`）——S3.2 兑换 / S3.3 过期扫描的覆盖索引。

#### 实现要点

| 项 | 决策 |
|---|---|
| 并发模型 | 账户**乐观锁**：`UPDATE ... WHERE userId=? AND version=?`，影响行数 0 → **整事务重试**（最多 3 次，带抖动退避）→ 409 `CONCURRENT_UPDATE`。批次扣减走条件更新 `WHERE remainingAmount >= N`（0 行 → 409 `BALANCE_NOT_ENOUGH`），与账户更新同事务，不会出现「批次扣了账户没扣」。**MySQL 瞬时死锁（1213）/锁超时（1205）也纳入重试**——实测两个并发录单会因「批次行锁 + 账户行锁 + 插入意向锁」交错触发死锁，不重试就是 500 |
| 一单只送一次 | 传 `orderId`/`orderNo` 启用幂等：事务内先查 + 唯一索引兜底，并发重复录单 → 1 成功 + 1×409 `ORDER_POINTS_ALREADY_EARNED`（实测余额 +200 而不是 +400） |
| 积分规则 | 商家级优先、其次平台级（`merchantId=0`）；`points = floor(amount × earnRatio)`；低于 `minAmount` → **201 + `earned:false`**（业务规则不是错误，理由：运营录单被 400 打断反而不知道该不该重试）；有效期 FIXED_MONTHS 按自然月 / YEAR_END 到 12-31；规则改动写 `audit_logs`（before/after），同一商家只能一条生效 → 409 `POINT_RULE_ALREADY_ACTIVE` |
| FIFO | `consumeFifo`：`SELECT ... FOR UPDATE` 取未过期（`expireAt > now`）且 `remainingAmount > 0` 的批次，`expireAt` 升序逐笔扣；返回逐笔明细给 S3.2 兑换 / S3.4 退款回退（方案 A：退回原批次保留原有效期）复用。人工负向调整同样走 FIFO——**不能通过调账把过期积分盘活** |
| 归属与隔离 | 商家 / 门店由 JWT 推导不信任入参：店员限本店（403 `STORE_NOT_OWNED`）、商家传别家 → 403 `FORBIDDEN_SCOPE`；**主体可用直属附属门店**（与核销同口径），积分记**门店所属商家**名下（对账口径）。附属查别家流水 / 无本店流水的用户 → 403 `FORBIDDEN_SCOPE`。主体商家可见无商家归属的人工调整流水（自己的运营动作），附属不可见 |
| 事件口径 | EARN（正，新批次）/ SPEND（负，FIFO）/ EXPIRE（负，S3.3）/ REFUND（正，回原批次，S3.4）/ ADJUST（带符号） |

#### 验收用例（31 条全过，证据 `docs/screenshots/s31-api-cases.txt`）

成功 13：账户列表（临期字段）/ 详情（`available` 40 ≠ `balance` 120，过期批次 `usable=false`）/ 录单送分（+100，有效期 +12 月）/ 余额精确累加 / 人工 +50 + ADJUST 流水 / 审计 / 流水 type 筛选×2 / 规则列表与修改（写审计）/ FIFO 扣减顺序（先扣 2027-04 批次再扣 2027-09 批次）/ 店员录单 / 附属录单。

此前几个模块的 raw 查询结果都要显式 Number 化。

### S3.2 积分兑换代金券（后端 + 前端，2026-10-07 交付待验收）

> S3.2 在 S3.1 的账户底座之上，把「积分 → 代金券」闭环打通。核心难点：**FIFO 跨批次扣积分 + 券码分配
> + 券实例生成 + 库存闸门** 必须在一个事务里全部成功或全部回滚，且**快速双击 / 并发**不能多发票、
> 不能多扣积分、不能把库存卖成负数。

#### 数据模型（schema 落地）

- 新增 `exchange_records` 表（`server/prisma/migrations/20261007100000_s32_exchange_record/migration.sql`，
  含幂等约束 `uniq_exchange_request` UNIQUE `(userId, requestId)`）：
  - 幂等键 `requestId`（前端 UUID）落库，唯一索引兜底并发重复提交；
  - 冗余 `pointsCost`（下单时模板快照）、`couponInstanceId`、`merchantId`、`channel` 便于对账。

#### 实现要点（9 步全同事务）

| 步 | 动作 | 失败语义 |
|---|---|---|
| ① | 幂等键命中 → 返回上次结果（200 + `idempotent:true`），不写数据 | 不报错 |
| ② | 模板校验：存在 / 上架 / 库存 / 限领 | 404 / 409 `TEMPLATE_NOT_AVAILABLE` / `STOCK_EXHAUSTED` / `PER_USER_LIMIT_EXCEEDED` |
| ③ | 可用积分预检（过期批次不算） | 409 `BALANCE_NOT_ENOUGH` |
| ④ | `consumeFifo` 扣积分 + 逐笔 SPEND 流水（指回券实例） | 409 `BALANCE_NOT_ENOUGH` |
| ⑤ | 券码 `FOR UPDATE` + 条件更新（并发下只有一个请求拿到同一码） | 409 `CODE_POOL_EXHAUSTED` |
| ⑥ | 生成券实例：issuer=模板归属商家（主体），source=EXCHANGE | — |
| ⑦ | 账户乐观锁扣减（冲突重试 3 次） | 409 `CONCURRENT_UPDATE` |
| ⑧ | 模板 `issuedCount` 条件更新（`WHERE totalStock-issuedCount>=1`） | 409 `STOCK_EXHAUSTED` |
| ⑨ | 兑换记录 + 审计 | — |

任一步失败 → 整事务回滚（用例 9 用 `BEFORE UPDATE` 触发器注入 `issuedCount` 写库失败验证：
积分未扣、券码未占用、无券实例 / 兑换记录 / SPEND 流水）。

### S3.3 积分过期清零 · 定时任务（后端 + 前端，2026-10-07 交付待验收）

> S3.3 补上积分生命周期的最后一块：**过期批次自动清零**。难点不是「扣钱」，而是三点——
> **幂等**（同一批次/同一天重复执行不重复扣）、**边界**（`expireAt < now` 用 UTC 比较，不重蹈 S2.4 时区坑）、
> **分批不锁表**（一次最多 500 条）。定时任务每天 01:00（Asia/Shanghai）自动跑，另留手动触发口子便于运营补跑。

#### 数据模型（schema 落地）

- `point_transactions` 新增 `sourceTransactionId`（`server/prisma/migrations/20261007120000_s33_point_expire/migration.sql`），
  EXPIRE 流水指回原 EARN 批次，前端据此展示「从 XX 批次过期 XX 积分」；
- 幂等唯一索引 `uniq_point_txn_expire_source` UNIQUE `(userId, sourceTransactionId, type)`——
  同一 EARN 批次只能有一条 EXPIRE 流水（`sourceTransactionId` **仅 EXPIRE 使用**、其余类型恒 NULL，MySQL 唯一索引允许多个 NULL，互不冲突）。
  **S4 收口修正**：S3.4 曾让 SPEND 复用 `sourceTransactionId`（指回被扣批次），导致同一用户从同一批次二次扣分撞此唯一键 → 500；现 SPEND/REFUND 改用新增列 `originBatchId`，`sourceTransactionId` 回归「仅 EXPIRE」，唯一索引保持不动（见「S4 收口反思」）；
- 扫描覆盖索引沿用 S3.1 的 `idx_point_fifo`（`(userId, expireAt, remainingAmount)`）。

#### 实现要点

| 项 | 说明 |
|---|---|
| 定时调度 | `@nestjs/schedule` + `@Cron('0 1 * * *', { timeZone: 'Asia/Shanghai' })`，北京时间每天 01:00；`timeZone` 显式锁定，容器 `TZ` 不影响触发时刻 |
| 手动触发 | `POST /tasks/points/expire`，需 `point:expire:trigger` 权限 + 写 `audit_logs`（`action=POINTS_EXPIRE`） |
| 扫描 | `type=EARN AND remainingAmount>0 AND expireAt<NOW()`；`expireAt` 为空（无有效期）天然不匹配，永不误过期 |
| 幂等 | ① 扫描只看 `remainingAmount>0`（清零后即被排除，重跑=0 笔）；② 条件更新 `WHERE id=? AND remainingAmount=?`（并发/重复只有 1 个成功）；③ 唯一索引 `(userId, sourceTransactionId, type)` 兜底 |
| 并发 | 服务内 `running` 互斥：两个手动触发同时进来，第二个直接返回 `skipped:true`（不重复处理） |
| 分批 | 每批 `take:500` 一个事务，处理完再取下一批，避免大事务锁表 |
| 账务 | 每批 EXPIRE 流水 `amount=-remaining`，账户 `balance -=` 且 `totalExpired +=`（乐观锁 version，冲突重试 3 次，`createMany` 批量写流水） |
| 边界 | 全程 UTC 比较（Prisma DateTime 存 UTC + `new Date()` 比较），`expireAt = now+1s` 不处理、`now-1s` 处理 |

#### 验收用例（15 条全过，脚本 `tmp-s33-cases.mjs`，证据 `docs/screenshots/s33-api-cases.txt`）

核心用例（对应需求）：
1. **幂等**：同一批触发两次，第一次 `processed=1/expired=100`，第二次 `processed=0/expired=0`，账户只扣一次、仅 1 条 EXPIRE；
2. **部分过期**：A(100)+B(50) 同时到期 → `balance -150`、生成 2 条 EXPIRE；
3. **边界时间**：`expireAt=+1s` 不处理（remaining 保持 40）、`expireAt=-1s` 处理（balance 清零）；
4. **混合状态**：同一用户 1 批已过期(30)+1 批未过期(+1d/40) → 只处理过期批，`balance 剩 40`、未过期批 remaining 不变；
5. **并发触发**：`Promise.all` 两个手动请求，一个 `processed=1`、另一个 `skipped:true`，无重复 EXPIRE；
6. **性能**：10000 条过期批次，`processed=10000`、耗时 **10.85s**（< 30s；`createMany` 批量写流水从 ~27s 优化到 ~10s）。

### S4.1 采购记录（后端 + 前端，2026-10-08 交付待验收）

#### 数据模型（复用既有 `purchase_records` 表，S4.1 无新增迁移）

- `purchase_records`（S2 已建）：`purchaseNo`（唯一）/ `mainMerchantId` / `subMerchantId` / `templateId` /

#### 实现要点

| 项 | 说明 |
|---|---|
| 单号 | `purchaseNo` = `{mainMerchantId}-{subMerchantId}-{yyyymmdd}-{seq}`（同 main-sub 同天 seq 递增），唯一索引兜底 |

#### 验收用例（16 条全过，脚本 `tmp-s41-cases.mjs`，证据 `docs/screenshots/s41-api-cases.txt`）

1. **单号格式**：`1-2-{yyyymmdd}-1`；同 main-sub 同天 seq 递增；不同 sub 独立编号；
2. **隔离**：附属只看到自己作为 sub 的（2 条），主体看到全部（3 条）；

4. **结算**：主体结算 → SETTLED；重复结算 → 409；附属结算 → 403；
5. **不可删除**：无 DELETE 端点（404/405）；
6. **并发生成**：5 并发新增同一 main-sub 当天采购，全部成功、`purchaseNo` 互不重复（`1-2-...-3..7`），无 500；
7. **结算审计**：`settle` 写 `audit_logs`（`PURCHASE_SETTLE`，before/after）；
8. **主体视角 = B**：主体=自己作为 main 或 sub 的；附属(sub02)只看到 sub=3，查别家(merchant 2) → 403。

#### 追问与边界决策（S4.2 前置）

- **purchaseNo seq 并发**：「读最新 +1」+ 唯一索引兜底（P2002）→ 捕获后**重读最新 seq 重试**（最多 5 次），并发不撞号、不留 500（用例6 验证 5 并发）。
- **settle 写审计**：是，`audit_logs` 一条 `PURCHASE_SETTLE`，带 before/after `settleStatus`（用例7 验证）。
- **主体视角口径 = B（自己作为 main 或 sub 的）**，不是「联盟内所有采购」：当前单主体系统下 main=1 命中全部（因每条采购 main 都是 1），但口径上仍按 B 收敛，避免未来多主体时跨主体可见。越权由附属 scope 校验兜底（用例8）。

### S4.2 对账账单（后端 + 前端，2026-10-09 交付待验收）

> 对账金额口径（MVP）：`settlement_amount = Σ（本期核销券的 face_value）`，**不含**「新客占比调整系数」
> （那是 v2 商业谈判后的规则，现在加是空转）。
> 核心约束：**快照一致性**（生成后数据再变不影响已出账单）、**幂等生成**、**状态机单向**、**数据隔离**。

#### 数据模型（复用既有 `settlement_reports` 表，S4.2 无新增迁移）

- `settlement_reports`：`reportNo`（唯一）/ `periodStart` / `periodEnd` / `merchantId`（null=全平台）/
  `reportType`（REDEMPTION）/ `totalCount` / `totalAmount` / `status`（GENERATING/GENERATED/CONFIRMED/DISPUTED）/
  `detail`（Json 快照）/ `generatedBy` / `generatedAt` / `confirmedAt`。
- `reportNo` 格式：`SET-{merchantId|ALL}-{yyyymmdd}-{yyyymmdd}`，如 `SET-2-20261001-20261101`。
- 唯一约束落在 `reportNo`；「同 (merchantId, period) 幂等」由应用层 `findFirst` 保证。

#### 实现要点

| 项 | 说明 |
|---|---|
| 金额口径 | 用数据库 `_sum(faceValue)` 聚合算总额，**不在应用层循环累加**（10000 条核销生成实测 ~1.4s） |
| 快照 | 生成时把本期「核销明细 + 采购明细」固化进 `detail`（Json），后续核销 / 采购变化不影响已生成账单 |
| 幂等 | 同 `(merchantId, periodStart, periodEnd)` 已存在且非 `DISPUTED` → 直接返回（不重复创建）；`DISPUTED` → 重新生成并刷新快照 |
| 状态机 | 条件更新 `UPDATE ... WHERE id=? AND status='GENERATED'` 作为并发闸门：`CONFIRMED` 再操作 → 409 `SETTLEMENT_FROZEN`；`DISPUTED` 直接确认 → 409 `SETTLEMENT_NOT_CONFIRMABLE`（须先重新生成） |
| 隔离 | 平台 / 主体看全量，附属只看自己；`assertVisible` 越权一律 **404**（不泄露存在性） |
| 定时任务 | `SettlementCronService`：每月 1 日 00:00（`Asia/Shanghai`）为每个附属商家生成上月账单（内部幂等，重复执行返回已存在） |
| 审计 | 生成 / 重新生成 / 确认 / 异议全部写 `audit_logs`（`module=settlement`，含 before/after） |

#### S4 收口反思（2026-10-10）

**一、本轮修复的两个真实缺陷**

| # | 缺陷 | 触发条件 | 根因 | 影响 |
|---|---|---|---|---|
| 1 | 同一 EARN 批次二次扣分 → 500 | 同一用户第二次从同一批次扣分兑换（FIFO 复用未扣完批次） | S3.4 让 SPEND 复用 `sourceTransactionId` 指回批次，撞 `@@unique(userId, sourceTransactionId, type)` | 合法兑换报 500 |

**三、S3.1 原始 31 条用例为何漏测「新用户并发」**

- 并发用例测的是什么：C1「同一订单并发」→ 幂等；C2「同用户两笔不同订单并发」→ 乐观锁不丢更新；C3「并发人工调整扣减」→ 不超扣。
- 「新用户并发」为何漏：账户是**隐式按需创建**（`ensureAccount`）。C1/C2/C3 的余额断言都建立在「用户已有积分账户」这一默认前提上，测试数据均从**稳态**（账户已存在）出发，没有人从「账户尚不存在」的冷启动时刻做并发。
- 性质：**边界正交组合的系统性遗漏**（不是省时）——并发维度测了，但没与「首次创建」维度交叉。

**四、测试用例设计原则（新增，纳入后续阶段）**

1. **并发用例必须覆盖「首次创建」场景**：任何 get-or-create / 隐式按需创建的资源，都要有「资源尚不存在时的并发创建」用例（冷启动竞态是高发区）。
2. **catch 必须精确匹配约束名 / 唯一键，禁止泛化**：`P2002 → 具体业务错误` 必须校验 `meta.target`；无法精确匹配时宁可重试或抛原始错误，也不误报业务码。
3. **边界要压到「最不利时刻」**：新用户首两笔、余额刚好够、批次刚好扣到 0、并发恰好同时到达——正常态要测，最不利态更要测。
4. **每个唯一约束都要有「命中即断言 reasonCode」的用例**，并在文档写清该约束冲突时对外返回什么。
5. 涉及「时间边界」的用例（如 +1s/-1s）在 Docker 等有延迟的测试环境下要留足余量，避免抖动。
