# 05 · 部署手册（Docker + Nginx）

架构：`浏览器 → gateway(Nginx:80) ─┬─ 静态资源（镜像内 dist，SPA 回退）
                                   └─ /api/v1 → server:3000（NestJS）→ mysql:3306`

| 服务 | 镜像 | 说明 |
|---|---|---|
| `mysql` | mysql:8.0 | 数据卷 `mysql-data`，`mysqladmin ping` 健康检查 |
| `server` | `shangmeng-server`（`server/Dockerfile`） | 启动时自动 `prisma migrate deploy`，依赖 mysql healthy |
| `gateway` | `shangmeng-gateway`（`deploy/Dockerfile.gateway`） | **内含前端产物**，SPA 回退 / 反代 / SSE / gzip，依赖 server healthy |
| `screen` | `shangmeng-screen`（`web/Dockerfile`） | 前端独立镜像，`profiles: [assets]`，默认不启动 |

---

## 一、关键设计决策

### 1. screen 与 gateway 的衔接：采用「gateway 多阶段构建自带 dist」（不挂共享卷）

| 方案 | 结论 |
|---|---|
| **A. gateway 多阶段 COPY 前端产物**（采用） | gateway 镜像在构建阶段跑一次 `npm run build -w web`，把 `dist` 打进镜像 |
| B. screen 导出 dist 到共享卷，gateway 只读挂载 | 备选，见下文「回退方案」 |

选择 A 的理由：

1. **无权限问题**：不需要在容器间协调 UID（nginx 镜像 worker 以 `nginx` 用户运行，共享卷常出现 403/只读不一致）；
2. **无残留问题**：不会残留上一版本的旧文件（共享卷方案升级时旧 chunk 不会自动删除）；
3. **无启动顺序耦合**：不需要 `service_completed_successfully` 这类"任务型容器"，少一个运行时容器；
4. **镜像自包含**：gateway 镜像可单独分发/回滚，不会出现"卷内容与镜像版本不一致"；
5. **代价可控**：多一次前端构建（约 30–60s），且只在构建期发生。

`screen` 镜像仍然保留（独立静态托管、发布对象存储、本地单独验证），但默认不参与运行时：

```bash
docker compose build screen                 # 只构建镜像
docker compose --profile assets up -d screen  # 需要时单独运行 → http://localhost:8080
```

> **回退到共享卷方案（B）时的硬性要求**（若将来改用）：
> 1. `gateway.depends_on.screen.condition: service_completed_successfully`；
> 2. screen 的拷贝命令必须以 **退出码 0** 结束（`cp -a ... && echo ok`，拷贝失败必须非零退出，否则 gateway 会带着空卷启动）；
> 3. 拷贝前处理权限：`chown -R nginx:nginx /share`（或统一 UID），否则 nginx 读不到；
> 4. gateway 启动前自检卷内容：`test -f /usr/share/nginx/html/index.html || exit 1`（可写入 gateway 的 entrypoint 或 healthcheck）；
> 5. 每次升级前清空卷：`rm -rf /share/*`。

### 2. Prisma 在 Alpine 上：`node:22-alpine` + `openssl` + `libc6-compat`

选择 alpine（镜像比 `node:22-slim` 小约 150MB+）。Prisma 查询引擎在 musl 上依赖 openssl，`libc6-compat` 提供 glibc 兼容层，避免 `libssl.so`/`libpthread` 缺失。若后续仍出现引擎加载失败，改用 `node:22-slim`（debian 系，无需 libc6-compat，体积更大）。

### 3. SSE 鉴权：JWT → 一次性 ticket → 按维度隔离

| 端点 | 鉴权 | 说明 |
|---|---|---|
| `POST /api/v1/sse/ticket` | **JWT**（`Authorization: Bearer`） | 返回 60 秒一次性 ticket（`SSE_TICKET_TTL_MS`） |
| `GET /api/v1/sse/notifications?ticket=xxx` | ticket | 服务端反查 `userId/merchantId`，**只推送该维度通知**；ticket 用后即废 |
| `POST /api/v1/sse/publish` | `x-api-token`（API_TOKEN） | 外部系统/内部通知模块推送，可带 `target:{userId,merchantId}` |
| `GET /api/v1/sse/stats` | `x-api-token` | 运维统计 |

`API_TOKEN` **仅用于外部系统对接**，后台用户不再使用它。
Nginx 对 SSE 路径关闭 `access_log`，并对日志中的 `ticket/token/access_token/password` 参数值脱敏为 `***`。

## 二、从零到跑起来（完整命令清单）

### 1）准备环境变量

```bash
cd "D:\shangmeng"
cp .env.example .env
# 必须修改：MYSQL_ROOT_PASSWORD / MYSQL_PASSWORD / DATABASE_URL 中的密码 / JWT_SECRET / API_TOKEN
```

> `DATABASE_URL` 的用户名密码必须与 `MYSQL_USER` / `MYSQL_PASSWORD` 一致，主机名为容器服务名 `mysql`。

> [!CAUTION]
> **上线前必读 —— 当前默认配置不能用于生产**
>
> 0. **`NODE_ENV` 必须是 `production`。** 默认规则是「没配就当生产」（`docker-compose.yml` 里 `${NODE_ENV:-production}`），`NODE_ENV=development` 只在 `.env` 里显式写才生效。**生产部署前必须确认容器内的值是 `production`**，否则 `GET /api/docs` 会对外暴露全部路由清单、参数结构与 Bearer 鉴权方式，等于把攻击面画好送给对方。
>    ```bash
>    # 部署后必查：容器内实际生效值必须是 production
>    docker compose exec server printenv NODE_ENV
>    # 期望：production
>
>    # 同时确认 Swagger 已关（应返回 404，不是 200）
>    curl -s -o /dev/null -w '%{http_code}\n' https://<你的域名>/api/docs
>    # 期望：404
>    ```
>    本地开发需要在 `.env` 写 `NODE_ENV=development` 才有 `/api/docs`。**不要把本地的 `.env` 拷到生产机器上。**
> 1. **`API_TOKEN` 默认值是示例值，上生产前必须替换。** 仓库默认值为 `please-change-api-token`，任何人拿到即可调用 `POST /api/v1/sse/publish`（向任意用户/商家推送事件）和 `GET /api/v1/sse/stats`（查看在线连接统计）。生产必须改为 **32 位以上随机字符串**，例如：
>    ```powershell
>    # PowerShell：生成 48 位十六进制随机串
>    -join ((1..48) | ForEach-Object { '{0:x}' -f (Get-Random -Maximum 16) })
>    ```
> 2. **生产环境应通过防火墙或 IP 白名单限制 `POST /api/v1/sse/publish` 与 `GET /api/v1/sse/stats`。** 这两个端点走 `x-api-token` 静态令牌，Token 一旦泄露无法按人撤销。建议在 Nginx 侧用 `allow <运维网段>; deny all;` 单独包一层 location，只放行内网/跳板机。
> 3. ~~`POST /api/v1/auth/dev-token` 临时调试端点~~ —— **已于 S1 收口时删除（docs/06 S1-C1）**。S1 期间它是凭请求体直接签发任意身份 JWT 的「万能登录后门」；现在调试/验收一律走真实 `POST /api/v1/auth/login`。
> 4. **上生产前必须轮换全部密钥（2026-10-17 追加）。** 本仓库早期按「上传全部文件」的要求，把 `.env` / `server/.env` 提交进过 git，其中含 **`MYSQL_ROOT_PASSWORD`、`MYSQL_PASSWORD`、`JWT_SECRET`、`API_TOKEN`、`DATABASE_URL`** 的真实值；2026-10-17 虽已把这些文件取消跟踪（见 `.gitignore`），但**已进入 git 历史的内容删不掉**。只要仓库曾公开或分享给他人，就必须视为已泄露：
>    - `MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD`：改 MySQL 账号口令，并同步 `.env` 与 `DATABASE_URL`；
>    - `JWT_SECRET`：换新值（会使所有已签发 token 失效，需重新登录）；
>    - `API_TOKEN`：换新值，并同步调用方（SSE publish / stats）。
>
>    注意：**仅改 `.env` 不够**——历史里的旧值仍然可读。若仓库要公开，需另用 `git filter-repo` / BFG 改写历史并强推（本次未执行，见 docs/00）。

**S1 收口项（已完成，2026-10-06）**：`/auth/dev-token` 端点已删除，删除后该路径返回 404；`/auth/login` 已验证可完整替代（含换取 SSE ticket）。

## 三、Nginx 关键配置

配置文件：`deploy/nginx/gateway.conf` → `/etc/nginx/conf.d/default.conf`

| 需求 | 配置 |
|---|---|
| SPA 回退 | `location / { try_files $uri $uri/ /index.html; }` |
| API 反代 | `location /api/ { proxy_pass http://shangmeng_api; }` |
| **SSE** | `location /api/v1/sse/`：`proxy_buffering off`、`proxy_cache off`、`proxy_read_timeout 3600s`、`proxy_send_timeout 3600s`、`chunked_transfer_encoding on`、`gzip off`、`access_log off` |
| gzip | `gzip on` + `gzip_types`（**不含** `text/event-stream`） |
| 日志脱敏 | 自定义 `log_format shangmeng`（不可命名为 `main`，与官方 nginx.conf 冲突），把 `ticket/token/access_token/password` 的值替换为 `***` |
| 长缓存 | `/assets/` 30d immutable；`/index.html` no-store |
| 上传 | `client_max_body_size 20m` |

修改配置后重载：`docker compose exec gateway nginx -s reload`（改镜像需 `docker compose up -d --build gateway`）。

## 五、常见问题

| 现象 | 排查 |
|---|---|
| server 反复重启 | `docker compose logs server`；多为 `DATABASE_URL` 与 MySQL 密码不一致 |
| server 健康检查失败但日志正常 | 容器启动会先跑迁移，首次较慢；`start_period: 40s` 已放宽，可再调大 |
| 页面刷新 404 | 确认 `deploy/nginx/gateway.conf` 已打进镜像：`docker compose exec gateway cat /etc/nginx/conf.d/default.conf \| findstr try_files` |
| 前端请求 404/连到 mock | 构建参数必须是 `VITE_USE_MOCK=false`、`VITE_API_BASE=/api/v1`，改完要 `docker compose up -d --build gateway` |
| SSE 连上就断 / 不实时 | 确认命中 `/api/v1/sse/`（非 `/api/`）；检查 `proxy_buffering off`；心跳 30s < `proxy_read_timeout 3600s` |
| SSE 提示 ticket 无效 | ticket 60 秒有效且一次性；重新走 `POST /sse/ticket` |
| Prisma 引擎加载失败 | 镜像已装 `openssl`+`libc6-compat`；若仍失败，把 `server/Dockerfile` 的基础镜像换成 `node:22-slim` |
| 端口占用 | 改 `.env` 的 `NGINX_PORT` / `MYSQL_PORT` / `SCREEN_PORT` |
| gateway 反复重启（`Restarting`） | 见下条：`docker compose logs gateway` 看 `[emerg]` 行 |
| gateway 日志 `nginx: [emerg] unknown "1" variable` | **Nginx 不支持用 `${N}` 引用正则捕获，必须写裸的 `$N`**。日志脱敏的 4 行 `set $log_query` 若写成 `"${1}ticket=***${3}"`，Nginx 会把花括号内当作**变量名**去查表注册，`1`/`3` 是捕获编号而非已注册变量，配置加载即失败并无限重启。正确写法：`"$1ticket=***$3"` |
| 改了 `gateway.conf` 但容器内仍是旧配置 | 配置是 `COPY` 进镜像的，**必须** `docker compose build gateway`（或 `up -d --build gateway`）重建，`nginx -s reload` 不够 |
| 想在起容器前先验证 Nginx 配置 | `docker run --rm --network shangmeng_shangmeng -v D:\shangmeng\deploy\nginx\gateway.conf:/etc/nginx/conf.d/default.conf nginx:1.27-alpine nginx -t`。**必须带 `--network`**，否则 `upstream` 里的主机名 `server` 解析不到，会误报 `host not found in upstream` |
| 改了 `schema.prisma` 后怎么生成迁移 | **已经把 migrations 挂进容器了**（`docker-compose.yml` 里 `./server/prisma/migrations:/app/server/prisma/migrations`），容器内 `npx prisma migrate dev --name xxx` 生成的 SQL 会**直接落到宿主仓库**。以前用的是逐文件拷贝方案：<br>`docker compose cp server:/app/server/prisma/migrations/<时间戳>_<名字> server\prisma\migrations\`<br>拷回/挂载生效后再 `docker compose build server` 重新构建镜像 |
| 上传的文件在哪 / 重建容器会不会丢 | MVP 落本地磁盘：`docker-compose.yml` 已把宿主机 `./uploads` 挂到容器内 `UPLOAD_DIR`（默认 `/app/uploads`），容器重建不丢。对外路径 `/uploads/年/月/<uuid>.<ext>` 由 Nginx `location /uploads/` 反代到后端，后端在 `main.ts` 用 `useStaticAssets` 以 `/uploads/` 前缀提供（**不经过 `/api/v1` 前缀**）。换 OSS 只需替换 `UploadService` 的实现 |
| 日志里出现明文 ticket | 确认日志格式是 `shangmeng` 而非 `main`；SSE location 已 `access_log off` |
| **`docker compose build` 报 `failed to resolve source metadata for docker.io/library/node:22-alpine`**（或 `failed to unpack image on snapshotter overlayfs: unexpected media type text/html`） | **BuildKit 无法解析/拉取基础镜像 `node:22-alpine`**（国内镜像源或代理返回了 HTML 而非镜像元数据）。<br>**绕过（已验证）：改用经典构建器** ——<br>`$env:DOCKER_BUILDKIT='0'; docker build -f server/Dockerfile -t shangmeng-server:latest .`<br>`docker compose up -d --no-build server`<br>gateway 同理：`$env:DOCKER_BUILDKIT='0'; docker build -f deploy/Dockerfile.gateway -t shangmeng-gateway:latest .` + `docker compose up -d --no-build gateway`。<br>**根治**：给 Docker 配置可用的 registry-mirror，或修复本机代理；`docker pull node:22-alpine` 同样失败即确认为环境问题（非代码问题） |

## 六、分步验收清单（首次部署严格按此顺序）

### 第 1 步：只构建，不启动

```bash
docker compose build server gateway screen
# 说明：直接 docker compose build 会构建全部服务（前端被构建两次：screen 与 gateway），耗时翻倍
```

验收：三个镜像均成功，无 `npm ci` 失败、无 Prisma 引擎下载失败、无 `vue-tsc` 报错。

| 常见报错 | 原因 / 处理 |
|---|---|
| `Cannot find module '@prisma/client'` | builder 阶段 workspace 解析问题；确认 `server/package.json` 中 `@prisma/client`、`prisma`、`ts-node`、`tsconfig-paths`、`typescript` **都在 dependencies** |
| `Error: Cannot find module 'libssl'` | runner 阶段的 `apk add --no-cache openssl libc6-compat` 必须在 `COPY --from=builder` **之前** |
| `COPY failed: no source files` | 构建上下文不对，必须回到**仓库根目录**执行 |

```bash
docker compose exec server curl -s http://127.0.0.1:3000/api/v1/health
# 期望：{"code":200,"message":"success","data":{"status":"ok",...}}
```

| 常见报错 | 处理 |
|---|---|
| `P1001: Can't reach database server` | MySQL 还没 healthy；确认 `depends_on.condition: service_healthy` 生效 |
| `P1003: Database does not exist` | `DATABASE_URL` 的库名与 `MYSQL_DATABASE` 不一致 |
| `P3009: migrate found failed migrations` | 之前失败过，`docker compose down -v` 清库重来 |
| seed 报 `Cannot find module 'typescript'` / `ts-node` | 二者必须在 dependencies（已在 S0 修正） |
| 迁移成功但表是空的 | 设计如此：启动只 `migrate deploy`，seed 需手动执行上面那条 |

| 常见报错 | 处理 |
|---|---|
| `/` 返回 403 | dist 权限问题；`Dockerfile.gateway` 中 `chown -R nginx:nginx /usr/share/nginx/html` 已加 |

| `/api/v1/health` 返回 502 | upstream 必须是 compose 服务名 `server:3000`；确认 server 已 healthy |

### 第 5 步：SSE 全链路

```bash
# 1) 账号密码登录拿 JWT（dev-token 已删除，见 docs/06 S1-C1）
curl -X POST http://localhost/api/v1/auth/login ^
  -H "Content-Type: application/json" ^
  -d "{\"username\":\"admin\",\"password\":\"Test@123456\"}"

# 2) JWT 换一次性 ticket（60 秒）
curl -X POST http://localhost/api/v1/sse/ticket -H "Authorization: Bearer <accessToken>"

# 3) 终端 A 保持连接
curl -N "http://localhost/api/v1/sse/notifications?ticket=<ticket>"

# 4) 终端 B 推送，重点验维度隔离
curl -X POST http://localhost/api/v1/sse/publish -H "x-api-token: 你的API_TOKEN" -H "Content-Type: application/json" -d "{\"event\":\"notification\",\"data\":{\"title\":\"发给商家2\"},\"target\":{\"merchantId\":2}}"
# → 终端 A（merchantId=1）不应收到
curl -X POST http://localhost/api/v1/sse/publish -H "x-api-token: 你的API_TOKEN" -H "Content-Type: application/json" -d "{\"event\":\"notification\",\"data\":{\"title\":\"发给商家1\"},\"target\":{\"merchantId\":1}}"
# → 终端 A 应收到 event: notification

# 5) 复用同一 ticket（一次性）
curl -N "http://localhost/api/v1/sse/notifications?ticket=<ticket>"
# → 403 INVALID_SSE_TICKET
```
